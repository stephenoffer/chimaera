# Ray 2.60 vs Chimaera: 3 nodes on one machine (2026-11-21)

`bench/evals/local_cluster.py`: three Ray nodes (`ray.cluster_utils.Cluster`) against three Chimaera peers, 4 CPUs each, on one Apple M3 Pro (12 cores, macOS 14.5). Both run the workloads of `bench/evals/multi_node.py` at `EVAL_SCALE=0.3`. Each value is the median of 3 rounds, alternating which runtime goes first. The Chimaera peer is the `dev` profile build (optimized, with debug info) of the working tree after the Raft log-gap fix.

**What this measures:** protocol and scheduling overhead across node processes. **What it does not:** scaling. All nodes share one machine's cores and loopback network, and other sessions were building and testing on the same machine during the run.

| Workload | Ray 2.60 | Chimaera | Better |
|---|---:|---:|---|
| Independent no-op tasks | 8,739/s | 4,959/s | Ray, 1.8x |
| CPU scaling efficiency (12 CPUs) | 0.60 | 0.73 | Chimaera |
| Map of tiny items, naive | 7,644/s | 246,776/s | Chimaera, 32x (Ray reaches 8.27M/s only with hand batching) |
| Large object to 24 readers | failed (see below) | 0.41 s | not compared |
| Actor calls, 8 actors | 15,894/s | 7,475/s | Ray, 2.1x |
| Nested tasks, 48 parents | 2.49 s | 0.89 s | Chimaera, 2.8x |
| Shuffle, 960k pairs, 64 to 64 partitions | 1.37 s | 1.40 s | parity |

Ray's broadcast failed in every round with `OutOfDiskError`: Ray refuses `ray.put` when the disk is over 95% full by its measure, and this shared laptop had about 28 GB free of 460 GB. That is a limit of this machine, not a Ray result.

The shuffle row comes from a separate 3-round run, after `Partitioned` became iterable by partition. The first run's Chimaera shuffle failed with `TypeError: 'Partitioned' object is not iterable`: `local3-shuffle-2026-11-21.json`.
