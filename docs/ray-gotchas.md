# Ray Core gotchas and what Chimaera does about them

These are problems Ray Core users commonly hit, and what Chimaera does about
each by default, with no option to set. "Handled" means a test or a measurement
in [qualification.md](qualification.md) shows it; "partly" says what is missing;
"open" means Chimaera does not avoid it yet.

## Memory and out-of-memory kills

| Ray problem | Chimaera | Status |
|---|---|---|
| Workers OOM-killed by the memory monitor, or by the kernel before the monitor acts; nodes over the threshold | Each function's private memory peak is learned; calls reserve it and wait for memory instead of overcommitting. Under host pressure the call furthest over its reservation is stopped (never the most recent), and its retry needs 1.5× the peak it reached | Handled: 12 of 12 memory-heavy calls with no kernel OOM kill where Ray finished 3 with 43 (3 GiB container) |
| The memory monitor reads host memory when a cgroup limit is unset, above host memory, or set on a parent; containers sized from host memory | The pool and CPU capacity take the tightest limit from the process's cgroup and every cgroup above it | Handled (unit test of the cgroup chain; container runs) |
| Many actors with tiny CPU requests exhaust a node's memory, since Ray schedules actors by CPU only | An actor's process starts only if what one actor of its class holds fits in the memory pool. That size is measured from the first ones started; until then a few start at a time (a quarter of the CPUs, but no more than the free pool holds at 512 MiB each, so a 32-CPU machine with a small pool does not start 8 at once). The rest wait with a reason, shown by `explain()` and `chimaera status`, that names the live actors holding the pool and says closing finished ones frees it. Closing them starts the next in turn | Handled: with a 600 MiB pool, 30 actors of 60 MiB each all started before (2.6 GiB in use); now 5 start and the rest wait (586 MiB). A test checks 12 actors of 150 MiB in a 1 GiB pool |
| Leaky workers, recycled by hand with `max_calls` | A worker whose memory between calls keeps rising is replaced, with a recorded decision | Handled |
| High RSS after objects are freed (allocator retention) | On Linux, a worker grown by 256 MiB hands freed memory back (`malloc_trim`) before the leak check reads it | Handled (fails with the trim disabled) |
| `memory=` and `num_cpus=` guessed by hand | Learned per function after a few calls; explicit values still win; `chimaera profiles` lists what was learned | Handled |
| Daemons on long-running clusters slowly grow | Soaks with one long-lived driver on a release peer (mixed calls: tiny calls, fresh arrays, puts, maps, actors). The peer's open files stay flat at 29, and stored arguments stay at 0 MiB: each blob is freed once its array is gone and its calls are done (before, +4 MiB per wave). Peer memory grew about 1.2 KB per call while a run lasted, because finished task records were kept whole. A released call's record now keeps only its outcome. The attempt log behind `explain()` held 200,000 records of about 3 KB, 700 MB; it is now also capped at 8 MiB encoded, about 25,000 recent attempts. After 750k tiny calls the peer's physical footprint is 213 MB, down from 833 MB. redb's default 1 GiB page cache per database (about 300 MB of the rest) is to be sized from the agent reserve | Partly: files, stored values, task records and the attempt log are bounded; the database cache is not sized yet, and there has been no multi-day run |
| Head node OOM when the driver builds and fetches a whole per-element DAG | No head node; `.remote()` waits for room once unfinished calls hold half the pool in arguments (CH110), and maps stream with a bounded window. A `ch.gather` whose results pass a quarter of the machine's memory warns once, while still reading, and names `ch.as_completed` and `fn.map` (CH117) | Handled (`test_values.py`): submission is bounded, and holding everything at once is warned about before it outgrows the machine |

## Objects and large values

| Ray problem | Chimaera | Status |
|---|---|---|
| The same large argument re-serialized on every call; large objects captured in closures | Arguments of 1 MiB or more are stored once by content; large captured values are warned about at submission | Handled: a 32 MiB array passed to 128 calls on 4 machines took 2.23 s against Ray's 3.07 s |
| Object store full or sized by hand; tasks waiting for plasma memory; the 200 GB cap; a small `/dev/shm` | One memory pool per peer instead of a fixed store; objects past 80% of it move to disk and stay readable; `/dev/shm` is used only when it has room | Handled (spill tested end to end on Linux) |
| Spill fills the disk; head-node disk saturation | Below 512 MiB free on the filesystem holding objects, new calls wait with a reason naming it (a fixed amount, so a large disk that is merely mostly full keeps working); a run's stored arguments are deleted when it ends; a full disk is named in the error with its free space | Handled (unit test; checked on a 700 MiB tmpfs) |
| Lost objects that cannot be rebuilt; `ray.get` hanging when the owner dies | Objects are replicated to a second peer; a value no peer holds raises `DataLost` instead of hanging | Partly: on Linux the replica copy currently races the first reader's fetch, so a peer can fetch an object twice (being fixed) |
| Accumulating every result before consuming any; objects kept alive after they are no longer needed | Maps keep a bounded number of items in flight; awaiting results one at a time in a loop warns (CH101); a `ch.put` value is deleted on every peer once its future is dropped and the calls that read it have finished, and so is an array passed straight to calls (on Linux each new array is stored separately), once the array is collected | Handled (`test_values.py`, `test_locality.py`) |
| Medium results (100–500 KB) of short tasks | A result is stored on the peer that produced it (in memory on Linux) and read there by the next call, without a copy through the driver | Handled (no setting to tune) |
| NumPy arrays from the object store are read-only: writing to an argument fails (`numpy-array-from-plasma-is-read-only`) | Arrays arrive writable and still zero-copy: a write copies only the pages touched and never changes the stored value | Handled (`test_values.py`) |
| Non-contiguous arrays (slices, transposes) lose zero-copy (guides: object-store) | A transposed array travels in its own order and a strided slice is made contiguous once when sent; both arrive as zero-copy views (128 MiB strided slice measured) | Handled (measured, no test) |
| Passing CUDA tensors between tasks | CPU tensors travel zero-copy. A CUDA tensor is copied through host memory, as torch's own pickling does, but it is rebuilt on the reader's granted GPU, or in a driver on its current GPU. Torch's pickling names the writer's device index, which fails to load where there is no GPU and can name a missing or wrong device where other GPUs are visible. A reader with no GPU gets the tensor on the CPU with a warning (CH112) | Handled; checked with a stand-in torch module (`test_values.py`), not yet on a GPU |
| A task receiving a list of unready references blocks and grows | Futures passed directly, or one level inside a list, tuple or dict argument, are dependencies: the call starts when they are ready and receives their values. `ch.handles(x)` passes them as futures instead | Handled (`test_api.py`) |

## Scheduling and resources

| Ray problem | Chimaera | Status |
|---|---|---|
| Work pending forever because actors or placement groups hold the resources | Actors hold no CPU by default; a waiting call says what it waits for, including CPU held by actors and their `cpus=` setting; a stalled wait prints the reason after a minute | Handled |
| Infeasible requests only warned about | A request no peer can satisfy fails at once with `ch.Infeasible` | Handled |
| Library thread pools oversubscribe cores; thread counts explode on large machines | OpenMP, BLAS, Polars, Numba and tokenizer pools are sized to the call's CPU grant | Handled |
| Tiny tasks cost more than they compute; lease churn saturates the raylet | Fast calls are batched automatically, and maps chunk their items, each item learned on its own | Handled: on 4 machines, maps of tiny items ran 194k items/s against 7k for Ray without hand batching |
| Slow task start while a fresh worker spawns | Executors start in parallel ahead of queued work | Handled |
| Nested `ray.get` starves workers; tasks blocked in `ray.get` pile up worker processes (`nested-ray-get-starves-workers`, `too-many-worker-processes-started`) | A call waiting on another gives back its CPU while it waits, so nested calls never deadlock, and its process runs other calls of the run meanwhile (hosting, `test_hosting.py`; `CHIMAERA_HOST_WHILE_WAITING=0` turns it off): a 3-way tree of depth 6 (364 waiting calls) ran in 4.0 s with at most 41 processes, where it took 11.6 s and 365 without. When waiting calls still hold many processes (at least 32, and 4 per CPU), the driver gets one line with the count, their memory and the fix; `chimaera status` shows the same | Handled (`test_hosting.py`, `test_defaults.py`) |
| Stragglers from cost skew in sweeps | Re-running slow calls would not help: an expensive parameter combination costs the same however often it runs. Its Ray-specific half, under-declared resources packing heavy tasks onto one node, is covered by learned CPU and memory reservations | Handled for the Ray-specific half; no speculative re-execution |
| Spread work for resilience; target node types by labels; scheduler tuning for large clusters | Placement weighs load, input locality and memory; labels with `Placement(require=, prefer=)`; there are no scheduler knobs to tune | Handled for labels and locality: quick readers of a `ch.put` value stay on its peer (`test_locality.py`; before, the value's holder was unknown and 512 readers of a 512 MiB value spread over 16 nodes) |
| Gang-scheduling collective workers | `ch.dist.reserve` bundles and gangs | Covered by the gang and reservation work (not part of this plan) |

## Workers, actors and processes

| Ray problem | Chimaera | Status |
|---|---|---|
| Too many open files | Each peer raises its open-file limit to the hard limit at start | Handled |
| Children of a killed worker survive | Each executor is its own process group, and stopping one stops the group | Handled (a child that calls `setsid` escapes) |
| Workers cache every dynamically defined function | The executor's code cache is bounded (256 entries) | Handled |
| Module-level CUDA allocation in every worker | Executors without a GPU grant see no GPU | Handled |
| Fork-based multiprocessing inside a task hangs | Executors keep Python's default start method: forkserver from Python 3.14, fork before it on Linux. Forcing forkserver would break pools of functions defined in the driver's script. Children that only compute work. A forked child that calls back into Chimaera (submit, wait, fetch) gets CH113 at once, instead of sharing its parent's connection, which would hang or lose outcomes. A child dropping its copy of a stored value no longer deletes the parent's files | Handled for children that call back or drop values (`test_values.py`); the start method stays Python's |
| Exceptions that cannot be unpickled; objects that cannot be pickled | An exception that cannot cross keeps its type name, message and traceback; captured values are checked before submission | Handled |
| An error from a call nobody reads vanishes; Ray Client never prints it | When the future of a failed call is dropped and nothing read its error, one stderr line names the function, where it was called and the error, as asyncio does for a task's exception never retrieved. Failed calls still held at exit are reported at exit. A read error stays quiet, as does one passed to another call (that call carries it), the rest of a `ch.get` that raised one of its errors, a cancelled call, and an actor's calls once the program closed it. Past 10 lines, the rest are counted at exit | Handled (`test_defaults.py`) |
| Nested Pydantic v1 models lose field values when passed as arguments, silently; a Pydantic 2 `ValidationError` raised in a task does not come back cleanly (`pydantic-v2-validationerror-not-wrappable`; guides: serialization) | Pydantic 2 models, nested ones included, arrive whole. A v1 model defined in the main script cannot travel (v1's compiled validators do not pickle by value): `.remote()` fails at once, saying to define the model in a module, where it travels by name and arrives whole. A `ValidationError` raised in a call arrives as itself, with its `errors()` | Handled (checked by hand with pydantic 2.14 and 1.10; the test in `test_defaults.py` skips where pydantic is not installed) |
| `RecursionError` while serializing a deeply nested argument (`python-recursion-depth-exceeded`) | A linked list or tree too deep to pickle fails at `.remote()` with an error naming the argument and saying to send it flat (nodes in a list, links as indices) and rebuild it in the call; 5,000 levels deep pickles fine | Handled (`test_defaults.py`) |
| Shared references inside a call's arguments are lost: the same list passed twice arrives as two lists, and bound methods of one object get separate copies | A call's arguments are pickled together, so objects shared between them stay shared in the callee | Handled (`test_defaults.py`) |
| Actor cleanup skipped when an actor is killed: `__del__`, `atexit` and shutdown hooks never run, leaving connections, locks and files behind (`design-actors-for-sigkill-termination`) | Closing an idle actor asks its process to exit (SIGTERM to its process group); a busy one stops outright, so a call still running fails as closed. The instance is dropped, so `__del__` runs, then `atexit` handlers; the process is stopped outright after 5 s | Handled (`test_defaults.py`) |
| A new actor per request or loop iteration: each is a new process that takes seconds to start (guides: tasks-and-actors, scheduling-internals) | Once 20 actors made at one line have each ended after at most two calls, within a minute of being made, one warning (CH121) at that line says to make a few once and reuse them (`Cls.pool(n)`), or to use a function if the actor keeps no state. Actors made once and reused, and named actors looked up again, stay quiet | Handled (`test_defaults.py`) |
| Blocking code inside an async actor method, `ray.get` included, stalls every other call on the actor's one event loop (`blocking-ray-get-inside-async-actor-warns`; guides: tasks-and-actors) | When one step of an async method holds the loop for over a second (the same coroutine still running a moment later), the driver is told once per method: which method, the line it is on, and the fixes (await non-blocking calls, such as `await fut` in place of `fut.result()`; `asyncio.to_thread`; or a plain `def`, which runs on a thread). Checked by hand for `.result()` inside an `async def` | Handled (`test_defaults.py`) |
| An actor method that waits for another call to the same actor hangs forever: the actor runs one call at a time (guides: tasks-and-actors) | The waited-for call fails at once with `ch.Infeasible`, saying it is a deadlock and how to avoid it (call the method directly, or give the actor concurrency); the actor keeps serving | Handled (`test_defaults.py`) |
| A streaming generator read a second time silently yields nothing (`materialize-objectref-generators-before-reuse`) | A stream or map result read to the end raises `RuntimeError` if iterated again, saying to keep the items with `list(...)`; a pass that stopped early goes on where it stopped | Handled (`test_defaults.py`) |
| Environment variables set for the driver are missing in workers (guides: unexpected) | A run passes only the variables it names (`ch.init(env=...)`, `CHIMAERA_ENV_PASSTHROUGH`), so secrets stay home. A call that fails on `os.environ[name]` for a variable the program has gets a note (CH122) saying how to pass it; only short digests of the names travel, never names or values | Handled (`test_defaults.py`) |
| `ray.get` and `ray.wait` from several driver threads need care (`driver-threads-may-call-get-wait-concurrently`) | Twelve driver threads submitting, waiting and getting at once all get their own results | Handled (`test_defaults.py`) |
| Keeping one array out of a returned list pins the whole returned object (`one-returned-element-pins-the-whole-return-object`) | A result's stored copy is freed once its future is dropped, even while arrays read from it live: with one of two 100 MiB arrays kept, the store went from 200 MiB to 0 (macOS). On Linux each large array is its own arena file, so a kept array keeps only its own pages (by design; not measured here) | Handled (measured on macOS) |
| `ray.init` is first-call-wins: a later call's `runtime_env` is silently ignored (`ray-init-first-wins-runtime-env`) | `ch.init(cluster=..., env=..., tenant=...)` after the first call raises, saying to call `ch.shutdown()` first to connect again with other settings | Handled (`test_defaults.py`) |
| `import ray` replaces the program's root logging handlers, patches `Logger.makeRecord`, and Ray's loggers do not propagate to the root (`import-ray-replaces-root-logging-handlers`, `import-ray-patches-logger-makerecord`, `ray-loggers-do-not-propagate-to-root`) | Importing and using Chimaera leaves the program's handlers, `makeRecord` and record factory as they were; calls log at the driver's level, to its stderr | Handled (`test_defaults.py`) |
| An ObjectRef rebuilt from bytes in another process fails or hangs: its owner is unknown there (`objectref-serialized-out-of-band-owner-unknown`) | A future names its call, whose outcome the peers keep: one pickled by one program is read by another while the run that made it lasts | Handled (`test_defaults.py`) |
| Workers run in `/tmp/ray/session_*`, not where the program was started, so relative paths fail (`worker-cwd-is-session-folder-not-submission-dir`) | Calls on the program's machine run in its working directory: `open("data.csv")` reads the same file there | Handled (`test_defaults.py`) |
| Named-actor get-or-create from several driver threads is not thread-safe (`named-actor-create-get-if-exists-is-not-thread-safe`) | `Cls.options(name=...).remote()` from eight threads at once gives one actor | Handled (`test_defaults.py`) |
| A function calling `exit()` or `quit()` fails to pickle, or `sys.exit()` takes the worker down (`site-builtin-exit-in-pickled-function`) | The call fails with the `SystemExit` as its error and the worker keeps serving | Handled (`test_defaults.py`) |
| An ObjectRef from before a re-init hangs (`objectref-invalid-after-reinit-hangs`, `stale-objectref-after-cluster-restart`) | A finished call's future still reads after `ch.shutdown()` and `ch.init()` | Handled (`test_defaults.py`) |
| Objects fail to move between aarch64 and x86 peers in a mixed-architecture cluster (guides: serialization) | Values travel as pickle protocol 5 with out-of-band buffers: NumPy records byte order in each dtype, and both architectures are little-endian; functions travel as bytecode, which depends on the Python version, not the CPU (CH115 names a version mismatch) | Not checked: no mixed-architecture cluster here |
| A path that exists where the program runs is missing on the worker that ran the call: "works on my machine" (guides: unexpected) | The program's files are not copied (its project's code is). A call that ran on another machine and fails on a missing file gets a note (CH123) naming the machine and saying to pass the contents (large ones through `ch.put`) or use storage every machine sees | Handled (`test_defaults.py`) |
| `ray.init()` with no address starts a new local instance instead of joining the running cluster (guides: advanced-tuning) | `ch.init()` uses `$CHIMAERA_CLUSTER`, `$CHIMAERA_ADDRESS` or the default cluster profile, else the machine's one local peer, which every program on it shares; `chimaera run` sets these for the program it starts | Doesn't apply |
| Threaded actors race on their state; calls from different callers interleave (guides: tasks-and-actors) | As in Ray, by design: an actor runs one call at a time unless it declares `concurrency`, and calls keep their order per handle. A one-at-a-time actor that waits on its own queued call fails fast (row above) | Same as Ray |
| Actors are not restarted by default, and a restart loses their state (guides: tasks-and-actors) | The default is also `restart="never"`; `restart="fresh"` starts it again (`test_recovery.py`), and a durable actor (`state=ch.durable.State()`) resumes from its last committed state (`test_durable.py`) | Same default as Ray, with durable state |
| Edits to a local module are ignored by remote tasks (`edited-module-not-seen-by-remote-tasks-pickled-by-reference`) | Each run carries a fingerprint of the project modules the driver loaded; edited code gets fresh workers, unchanged code keeps warm ones | Handled (`test_learning.py`) |
| `ray.cancel` is best-effort and cancelling a task leaves the tasks it started running (guides: antipatterns) | Cancelling a call cancels the calls it started; a call that does not stop by itself is interrupted after 2 s and its worker stopped after 5 s | Handled (`test_api_tier1.py`, `test_spread_cancel.py`) |
| Actors dying, failing in `__init__`, or dying with their owner; restart failing when a creation argument was evicted; detached actors leaking | Creation arguments are kept until the run ends; actors end with their run unless detached | Handled for argument eviction; actor lifecycle is the actor API's |
| Workers crashing | Calls lost to a dead worker are retried (three attempts); an external effect reports `OutcomeUnknown` | Handled |
| Retrying transient application errors | `retry_exceptions` lists the exceptions to retry; your own exceptions are never retried otherwise | Handled (same choice as Ray) |

## Setup, versions and configuration

| Ray problem | Chimaera | Status |
|---|---|---|
| Calling an actor method like a local one: `c.inc(1)` instead of `c.inc.remote(1)` | The error names the method and the call to make: "Counter.inc runs in the actor, not here: call it with .inc.remote(...), which returns a future". Before, it was Python's "'RemoteMethod' object is not callable" | Handled (`test_defaults.py`) |
| "Lost reference to actor" from a handle never stored in a variable: `Counter.remote().inc.remote()` | Not a failure here: an actor lives for its run (or until closed), not as long as a handle does, so a call through a temporary handle works | Handled (`test_defaults.py`) |
| Async actors with very high concurrency: keep `max_concurrency` near 1,000–2,000 and scale out with more actors | An async method in an actor with `concurrency` above 1 runs as a task on the actor's event loop and holds no thread while it awaits. Before, every awaiting call held a thread (500 calls, 505 threads), which a pod's task limit would also stop. Four threads start and finish async calls. 1,500 calls awaiting at once use 9 threads, finish together in 3.3 s, and each sees its task context | Handled (`test_defaults.py`) |
| A remote function defined inside a loop: per-call `ray.remote(fn)` makes a scheduling class per task and can stall the cluster | No scheduling classes to explode. A new function per call is still pickled and hashed each time (2,000 calls: 0.84 s against 0.14 s through one function). After 100 functions with the same code, a warning names the function and says to define it once (CH120). The per-program cache of function digests is now bounded, where it kept every per-call lambda alive | Handled (`test_defaults.py`) |
| No GPU in a task or actor that did not ask for one: CUDA sees none, and the error never says why | Calls that ask for no GPU are shown none on machines that have them (so a CPU call never grabs one). When CUDA then fails in such a call ("No CUDA GPUs are available", "no CUDA-capable device", JAX's backend error), the error gets a note (CH119) saying the call asked for no GPU and how to ask for one | Handled (`test_defaults.py`, simulated; no GPU here) |
| Large shared data kept as Python lists, dicts or sets: every reader unpickles a full copy | Stored once like any large argument, but a collection that pickles to 8 MiB or more, passed to calls or stored with `ch.put`, warns once per call site (CH118). The warning says each reader gets a full copy and that a NumPy array or Arrow table is mapped and shared instead | Handled as a warning: the data structure stays the program's choice (`test_values.py`) |
| Ray crashes or `ray.init` hangs with "Resource temporarily unavailable" (EAGAIN) in a pod: its task limit is reached | The peer reads the tightest `pids.max` up its cgroup chain, also in a container that mounts only its own cgroup without a cgroup namespace (found from the mount's root in mountinfo). It starts another worker only when the limit has room for it; otherwise calls wait, and their wait reason names the limit and how to raise it. `chimaera status` lists the limit among its automatic settings. A start that still fails with EAGAIN says why | Handled: under `docker --pids-limit=24` with 4 CPUs, 32 calls finish in 6.7 s; before, they failed as "executor process exited" (`test_defaults.py`, Linux) |
| Driver and cluster on different versions | A program that would start a different peer binary than the one serving it warns once (CH111). The wire version is checked on connect. A remote cluster on another Chimaera version warns once (CH116). A remote cluster's workers run its own Python, so they learn the program's Python version, and a function that will not load there says the versions differ and how to fix it (CH115), instead of failing with a bare bytecode error | Handled (`test_defaults.py`, `test_cluster.py`); the Python mismatch is simulated, since only one Python is installed here |
| Port conflicts | A local program reaches its peer through a Unix socket, so no port is involved | Doesn't apply locally |
| Runtime environments: package size, setup timeouts, evicted packages, oversized inline settings, credentials | Project shipping and environments are the layered API's (`_project.py`) | Not part of this plan |
| A project's ignored files (data, checkpoints, `.env`) uploaded with its code, or failing the size limit (`runtime-env-uploads-respect-gitignore-unless-overridden`, `runtime-env-package-too-large`) | A project in a git work tree ships only what git would track: files it tracks and untracked files that `.gitignore` does not exclude, under git's own rules. Past 100 MiB, `ch.init` names the largest files. Done by the layered API (`_project.py`) | Handled (`test_project.py`) |
| Worker logging goes nowhere | Task log records reach the driver at the driver's level | Handled |
| System settings set in the wrong place | Automatic settings are derived at start and printed by `chimaera status` | Handled |
| `ray.get` timeouts | A wait that times out leaves the call running; a stalled wait says why after a minute | Handled |
| Ray-specific infrastructure: protobuf conflicts, dashboard agents, Ray Client, worker registration, native ABI crashes, State API imports, compiled graphs, constraints files, connectivity preflight | These concern Ray's own components, or GPU and pool features other parts of the plan own | Doesn't apply, or not part of this plan |

## What is still open

- Speculative re-execution of stragglers.
- A warning when CUDA tensors are passed between calls.
- Fork-based multiprocessing inside tasks keeps Python's default start method.
- On Linux, a replica copy that races the first reader's fetch of the same object.
